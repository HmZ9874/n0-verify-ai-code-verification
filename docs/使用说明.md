# N0 Verify 中文使用说明

N0 Verify 用独立、可复现的证据检查代码修改，尤其适合验证 Claude Code、Codex、Cursor、Gemini CLI 等编程 Agent 的完成声明。

## 1. 环境要求

- Node.js 20 或更高版本
- Git
- 项目自身需要的语言与包管理工具
- Docker（仅 `container` 模式需要）

检查当前环境：

```bash
n0-verify doctor
```

## 2. 安装与运行

发布到 npm 后可直接执行：

```bash
npx n0-verify demo
npx n0-verify check --base HEAD~1
```

从源码运行：

```bash
npm install
npm run build
node dist/cli-entry.js demo
```

也可以全局安装：

```bash
npm install --global n0-verify
n0-verify --version
```

## 3. 一分钟体验

```bash
n0-verify demo
```

Demo 会创建受控场景并展示 N0 Verify 如何发现：

- 删除测试；
- 添加跳过测试；
- 使用 `.only` 只运行部分测试；
- 使用 `|| true` 隐藏测试失败；
- 新测试无法区分旧实现和新实现。

Demo 不需要账号、API Key 或真实编程 Agent。

## 4. 初始化仓库

在 Git 仓库根目录运行：

```bash
n0-verify init
```

N0 Verify 会检测语言、包管理器以及构建、测试、lint 和类型检查命令，并生成：

```text
.n0/
├── n0.config.yml
├── requirements.yml
├── policies/
│   └── default.yml
└── waivers.yml
```

指定语言或同时生成 GitHub Actions 工作流：

```bash
n0-verify init --language typescript
n0-verify init --language python --ci github
```

支持的语言提示包括 `javascript`、`typescript`、`python`、`go` 和 `rust`。

`--force` 会覆盖现有 N0 配置文件，使用前应提交或备份已有配置：

```bash
n0-verify init --force
```

## 5. 执行验证

检查上一个提交到当前提交之间的变化：

```bash
n0-verify check --base HEAD~1 --head HEAD
```

检查当前分支相对主分支的变化：

```bash
n0-verify check --base origin/main
```

输出完整 JSON：

```bash
n0-verify check --base origin/main --json
```

同时把结果保存到文件：

```bash
n0-verify check --base origin/main --json --output n0-result.json
```

严格模式会把警告升级为阻断：

```bash
n0-verify check --base origin/main --strict
```

默认会生成 Proof Pack。临时不生成：

```bash
n0-verify check --base origin/main --no-proof
```

指定证据输出目录：

```bash
n0-verify check --base origin/main --proof-output ./n0-artifacts
```

## 6. 选择执行模式

### Audit 模式

```bash
n0-verify check --base origin/main --mode audit
```

只分析 Git diff、配置和测试篡改，不执行仓库代码。适合首次检查未知或不可信仓库。

即使提供 `--test-command`，Audit 模式也不会执行它。

### Clean Worktree 模式

```bash
n0-verify check --base origin/main --mode worktree
```

在临时 Git worktree 中执行 Base、Head、四象限矩阵和负向验证，可隔离未提交文件和工作目录残留。它是干净工作区，但不是安全沙箱。

### Container 模式

```bash
n0-verify check --base origin/main --mode container
```

需要 Docker。默认使用：

- 只读源代码挂载；
- 一次性内存工作区；
- 非 root 用户；
- 只读容器根文件系统；
- 清空 Linux capabilities；
- CPU、内存和进程限制；
- 默认关闭网络；
- 不传递宿主机秘密环境变量。

容器镜像和资源预算在 `.n0/n0.config.yml` 中配置。

## 7. 自定义可信命令

`.n0/n0.config.yml` 示例：

```yaml
version: 1
execution:
  mode: worktree
  network: false
  timeout_seconds: 120
  max_memory_mb: 4096
  max_cpu: 2
commands:
  install: npm ci --ignore-scripts
  build: npm run build
  lint: npm run lint
  typecheck: npm run check
  test: npm test
  coverage: npm run coverage
matrix:
  enabled: true
negative_control:
  enabled: true
  max_mutants: 10
  changed_lines_only: true
```

Pull Request 验证读取 Base 分支中的配置。PR 自己修改的配置不能降低本次检查强度。

临时覆盖测试命令仅适用于执行模式：

```bash
n0-verify check --mode worktree --test-command "node --test"
```

## 8. 验证 Agent 完成声明

让编程 Agent 把完成总结保存为 Markdown、YAML 或 JSON，然后运行：

```bash
n0-verify check --base origin/main --claims agent-summary.md --mode worktree
```

`--task` 是同义入口：

```bash
n0-verify check --base origin/main --task issue.md --mode worktree
```

Markdown 示例：

```markdown
- Implemented token expiration handling
- Added tests for expired tokens
- All tests pass
```

N0 Verify 只把文字转换为待验证声明；最终结果由仓库证据决定，而不是由另一个 LLM 决定。

## 9. 定义需求

编辑 `.n0/requirements.yml`：

```yaml
version: 1
requirements:
  - id: AUTH-01
    statement: Expired access tokens must be rejected
    severity: critical
    mandatory: true
    evidence:
      - runtime_test
      - negative_test
    paths:
      - src/auth/**
    tests:
      - tests/auth.test.ts
    must_fail_on_base: true
```

常用证据类型包括：

- `file_change`
- `test_diff`
- `runtime_test`
- `clean_test_run`
- `regression_test`
- `negative_test`

强制需求没有足够证据时，结果不会被标记为已支持。

## 10. 配置豁免

豁免必须位于可信 Base 分支的 `.n0/waivers.yml`：

```yaml
version: 1
waivers:
  - rule: N0-TEST-014
    path: tests/legacy/**
    reason: Legacy test suite migration
    approved_by: maintainer@example.com
    expires: 2026-10-01
```

过期、路径不匹配或由当前候选分支自行添加的豁免不会生效。有效豁免会在报告中显示为 `WAIVED`，不会静默隐藏。

## 11. 理解结果

证据状态：

| 状态 | 含义 |
| --- | --- |
| `SUPPORTED` | 现有可复现证据支持声明 |
| `CONTRADICTED` | 找到了与声明冲突的证据 |
| `INCONCLUSIVE` | 证据不足或环境阻止验证 |

策略判定：

| 判定 | 含义 |
| --- | --- |
| `PASS` | 可信策略允许该修改 |
| `WARN` | 存在需要审查的非阻断发现 |
| `BLOCK` | 存在阻断级违规或失败 |

两组状态彼此独立。例如，静态审计没有发现违规时可能得到 `PASS + INCONCLUSIVE`：策略没有阻断，但尚无运行证据证明行为正确。

CLI 退出码：

| 退出码 | 含义 |
| ---: | --- |
| `0` | 通过或允许的警告，且证据不是不确定状态 |
| `1` | 策略阻断 |
| `2` | 证据不充分或环境阻断 |
| `3` | 配置、用法或内部工具错误 |

## 12. 查看报告和证据包

默认输出目录：

```text
.n0/runs/<run-id>/
```

查看最近一次报告：

```bash
n0-verify report --format html
n0-verify report --format json
n0-verify report --format sarif
```

指定运行记录：

```bash
n0-verify report --run <run-id> --format html
```

HTML 报告是可独立打开的单文件。Proof Pack 还包含 manifest、Git diff、命令证据、日志哈希、需求矩阵、测试矩阵、Mutation 结果、SARIF 和 Badge。

## 13. 签名和验证 Proof Pack

生成 Ed25519 密钥：

```bash
n0-verify proof keygen
```

默认生成：

```text
.n0/signing-key.pem
.n0/signing-key.pub.pem
```

私钥不应提交到 Git。

生成签名证据包：

```bash
n0-verify check --base origin/main --signing-key .n0/signing-key.pem
```

验证哈希、文件完整性和签名：

```bash
n0-verify proof verify .n0/runs/<run-id>
```

## 14. 基线管理

```bash
n0-verify baseline create
n0-verify baseline inspect
n0-verify baseline update
```

基线记录当前提交和测试库存，用于审计已知状态。更新基线前应先人工确认变化可信。

## 15. GitHub Actions

可通过初始化生成工作流：

```bash
n0-verify init --ci github
```

也可以直接使用仓库的 JavaScript Action：

```yaml
permissions:
  contents: read
  pull-requests: write

steps:
  - uses: actions/checkout@<PINNED_COMMIT>
    with:
      fetch-depth: 0
  - id: n0
    uses: your-org/n0-verify@<PINNED_N0_COMMIT>
    with:
      base: ${{ github.event.pull_request.base.sha }}
      head: ${{ github.event.pull_request.head.sha }}
      mode: worktree
      strict: true
      github_token: ${{ github.token }}
```

Action 会写入 Step Summary、输出 Proof Pack 路径，并在提供 Token 时更新同一条 PR 评论。Fork PR 默认降级到 Audit 模式，避免执行不可信代码。

完整的 Artifact 上传示例见 [GitHub Action 集成](github-action.md)。

## 16. Benchmark 和开发验证

```bash
npm run lint
npm run check
npm test
npm run bench
npm pack --dry-run
```

Benchmark 包含 20 个欺骗或错误案例、10 个正常案例和 10 个模糊案例。它是确定性控制语料，不代表所有公共仓库上的普遍准确率。

## 17. MCP 和自动化集成

启动 stdio 服务：

```bash
n0-verify serve
```

提供的工具包括：

- `n0_check`
- `n0_doctor`
- `n0_runs`
- `n0_proof_verify`

可用于“Agent 编码 → N0 Verify 检查 → 把证据反馈给 Agent → 再次验证”的外部循环。

## 18. 常见问题

### Docker 不可用

运行 `n0-verify doctor`。如果 Docker 不在 PATH，请安装并启动 Docker，或者改用 `audit`/`worktree` 模式。

### Base 引用不存在

先获取完整 Git 历史：

```bash
git fetch --all --prune
n0-verify check --base origin/main
```

GitHub Actions 中 `actions/checkout` 必须设置 `fetch-depth: 0`。

### Audit 模式结果是 INCONCLUSIVE

这是正常且诚实的结果。Audit 模式没有执行测试，通常只能证明“没有发现策略违规”，不能证明运行行为正确。使用 `worktree` 或 `container` 模式获取运行证据。

### Base 本身失败

N0 Verify 会把基线问题与候选提交引入的问题分开，并返回 `INCONCLUSIVE` 或 `PRE_EXISTING`，避免把已有失败错误归责给当前修改。

### 报告可能包含敏感内容

Proof Pack 可能包含 Git diff、命令和日志。上传前应按源代码制品进行访问控制和保留策略审查。
